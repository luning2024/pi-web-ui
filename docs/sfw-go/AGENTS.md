## 评审门

设计方案类产物的默认状态是 **「草案，待评审」**。

- 用户明确说「开始做 / 可以做 / 动手」之前，**不写实现代码**。
- 不确定是否已获批时，按未获批处理，先问。

## 开发准则

### 1. 先想再写（Think Before Coding）

**不假设。不藏困惑。摊开取舍。**

- 明确陈述假设；不确定就问。
- 存在多种理解就摆出来，不要自己挑一个默默做掉。
- 有更简单的做法要主动说；该反对时反对。
- 不清楚就停下来，指出哪里不清楚。

### 2. 最简优先（Simplicity First）

**只写解决问题的最小代码。**

- 不加没要求的特性、抽象、可配置性。
- 不为不可能发生的场景写错误处理。
- 200 行能写成 50 行就重写。
- 问自己：资深工程师会觉得这过度设计吗？

### 3. 外科手术式改动（Surgical Changes）

**只碰必须碰的。只清理自己造成的。**

- 不顺手「改进」旁边的代码、注释、格式。
- 不重构没坏的东西；匹配既有风格，哪怕你自己写法不同。
- 注意到无关死代码**说出来，不要删**。
- 改完只清理**自己**造成的孤儿引用。
- 只按路径 `git add <具体文件>`，不要 `git add -A`。

### 4. 目标驱动执行（Goal-Driven Execution）

**把任务转成可验证的目标，循环到验证通过。**

- 「加校验」→「先为非法输入写测试，再让它通过」。
- 「修 bug」→「先写复现测试，再让它通过」。
- 多步任务先列 `[步骤] → verify: [检查]`。

这套准则**偏向谨慎而非速度**。琐碎任务自行判断。
如果 diff 里出现与请求无关的行，第 3 条就被违反了。
